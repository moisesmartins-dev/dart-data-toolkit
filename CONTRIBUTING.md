# Contributing to Dart Data Toolkit

Thank you for considering contributing to this project!

## Reporting Bugs

Before creating a bug report, please check if the issue has already been reported. If you found a bug:

1. **Use a clear and descriptive title**
2. **Describe the exact steps** to reproduce the problem
3. **Provide specific examples** to demonstrate the steps
4. **Describe the observed behavior** and **what you expected**
5. **Include screenshots/videos** if possible
6. **Mention your version** of the plugin, IDE, and OS

## Suggesting Features

Feature suggestions are always welcome! To suggest a feature:

1. **Use a clear and descriptive title**
2. **Provide a detailed description** of the suggested feature
3. **List some examples** of how it would be used
4. **Explain why** this feature would be useful

## Pull Requests

### Preparation
1. Fork the repository
2. Clone your fork locally
3. Create a branch for your feature
   ```bash
   git checkout -b feature/AmazingFeature
   ```

### Development
1. **Follow the Kotlin style guide**
2. **Add tests** where possible
3. **Update documentation** if necessary
4. **Keep commits clean and descriptive**

### Submission
1. Push to your branch
   ```bash
   git push origin feature/AmazingFeature
   ```
2. Open a Pull Request
3. Describe your changes clearly
4. Reference related issues (e.g. "Closes #123")

## Style Guides

### Kotlin Style
- Use descriptive variable names
- Prefer `val` over `var` when possible
- Use comments to explain complex logic
- Follow Kotlin naming conventions

### Commit Messages
- Use the imperative mood ("add feature" not "added feature")
- Limit the first line to 50 characters
- Reference issues and pull requests generously

Example:
```
Add support for @freezed classes

- Analyze @freezed annotation
- Generate appropriate methods for freezed classes
- Add tests for freezed support

Closes #123
```

### Documentation
- Keep README.md up to date
- Add comments in complex code
- Document changes in CHANGELOG.md

## Review Process

All PRs go through review before being merged:

1. **Build status** — the PR must pass all builds
2. **Code review** — at least one maintainer must review
3. **Tests** — test coverage must be maintained
4. **Documentation** — docs must be up to date

## Questions?

- 💬 Discussions: Open a Discussion on GitHub
- 🐛 Issues: Feel free to post questions as issues
